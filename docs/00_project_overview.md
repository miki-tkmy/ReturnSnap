# プロジェクト概要 (00_project_overview.md)

## 1. プロジェクトの目的

ReturnSnapは、現場から返却された仮設機材の写真をスマートフォンで撮影し、伝票番号・Base・作業区分ごとに自動整理してGoogle Driveへ保存する業務用Webアプリです。

現在は、協力会社がデジタルカメラで撮影した写真を、フロントメンバーがパソコンへコピーし、画像を圧縮して、日付別・伝票番号別のフォルダへ手作業で振り分けています。ReturnSnapでは、この転送・圧縮・フォルダ作成・振り分け作業を自動化し、フロントメンバーの定型作業を大幅に削減します。

アプリは次の2種類に分けます。

- **ReturnSnap Count**  
  協力会社の員数担当者が、伝票ごとの返納品全体写真を撮影するためのアプリ。
- **ReturnSnap Lift**  
  リフトマンが、返却資材の荷下ろし写真および返却荷姿の評価写真を撮影するためのアプリ。

GitHub Pagesをフロントエンド、Google Apps ScriptをGoogle Drive・Googleスプレッドシート連携用のバックエンドとして使用します。撮影データは端末内へ一時保存し、通信できない状況でも撮影・確認・削除・再撮影を継続できるようにします。通信確認後に利用者がアップロード操作を行い、保存が完了するまで端末内の未送信データを保持します。

## 2. ターゲットユーザー

### ReturnSnap Count

- 協力会社で返納仮設機材の仕分け・員数を行う作業者
- 60歳以上の利用者が多く、スマートフォン操作に不慣れな人を含む
- 個人名ではなく、端末ごとの固有名で管理する
- 初期導入は約10台
- 暫定端末名は次のとおり
  - 協力会社A_A
  - 協力会社A_B
  - 協力会社A_C
  - 協力会社A_D
  - 協力会社A_E
  - 協力会社A_F
  - 協力会社A_G
  - 協力会社A_H
  - 協力会社A_I
  - 協力会社A_J

### ReturnSnap Lift

- 返却資材を荷下ろしするリフトマン
- 個人専用の貸与iPhoneを使用する
- 初期導入は約4台
- 暫定撮影者名はA・B・C・D
- 端末と撮影者を初回登録時に紐付け、毎回の氏名入力は不要とする

### 管理者・フロントメンバー

- Base・端末・撮影者・荷姿基準を管理する担当者
- Google Drive上の写真とスプレッドシートのログを確認する担当者
- 必要に応じてGoogle Driveの日付フォルダを社内共有フォルダへ移動する担当者

## 3. ゴールと成功の定義

### 業務面のゴール

- デジタルカメラからパソコンへの写真コピー作業をなくす
- 写真の手動圧縮作業をなくす
- Base・日付・伝票番号・撮影区分ごとのフォルダ作成と振り分けを自動化する
- フロントメンバーの作業を、原則としてGoogle Driveから社内共有フォルダへ移す作業だけにする
- 伝票への転記漏れや確認不足があった場合に、伝票単位の写真から確認できる状態を作る
- 荷姿評価と画像を結び付け、ユーザーや返却元へ具体的な改善説明ができる状態を作る

### 利用面のゴール

- 高齢の利用者でも、説明を読まなくても基本操作を進められる
- ReturnSnap Countの基本操作を次の5工程以内に収める
  1. QRを読む、または伝票番号を入力する
  2. 写真を撮る
  3. 写真を確認する
  4. 不要写真を削除または撮り直す
  5. 保存する
- Base選択は初回設定時だけとし、通常画面では小さく表示する
- 員数用とリフトマン用を別アプリとしてホーム画面に追加し、作業区分の選択間違いを防ぐ
- 写真アプリへ保存しなくても、ReturnSnap内で撮影直後の確認・削除・再撮影ができる

### オフライン・信頼性の成功条件

- 通信がない状態でも、QR読取、手入力、撮影、写真確認、削除、再撮影、下書き保存ができる
- 撮影した写真は、シャッター操作直後に端末内のIndexedDBへ保存される
- アプリを閉じたりiPhoneを再起動したりしても、未送信データを復元できる
- Google Driveとログの保存完了が確認できるまで、端末内の未送信画像を削除しない
- アップロード途中で通信が切れても、保存済みの画像を重複させず、未保存分だけ再送できる
- プライベートブラウズや保存機能が利用できない状況では、撮影を開始させず、理由と対処方法を表示する
- Wi-Fiまたはモバイル回線への接続を利用者が確認した後にのみアップロードを開始する

### データ保存の成功条件

- 写真が次の構成でGoogle Driveへ保存される

```text
Baseコード
└ 年
   └ 月
      └ 撮影日
         └ 伝票番号
            ├ 員数
            ├ 返却資材
            └ 荷姿
               ├ A
               ├ B
               ├ C
               └ D
```

- QR読取時は`code=DLW024141-00`のような値を正しく抽出できる
- 手入力時は数字6桁のみを受け付け、端末Baseを付けた`DLW024141`形式に変換できる
- 先頭が0の伝票番号を欠落させない
- 端末Baseと伝票Baseが異なる場合も保存でき、警告と不一致ログを残す
- 画像を長辺2000px、JPEG品質0.9で保存する
- 1回の登録につき最大30枚を扱える
- 同じ伝票番号が既に存在する場合は、既存の伝票フォルダへ追加保存する

### 荷姿撮影の成功条件

- A・B・C・Dの全評価を選択できる
- 「荷姿基準」ボタンから、オフラインでも判定基準を確認できる
- 判定は「該当束数」と「トラック全体に占める割合」の悪い方を採用する基準を表示する
- 荷姿撮影では、全体写真1枚以上、細部写真2枚以上を必須とする
- 必須枚数を超えて全体・細部を追加撮影できる
- 最低枚数に達していない場合は保存できない
- D判定の例外条件を目立つ形で表示する

### セキュリティ・運用の成功条件

- GitHub Pagesの公開リポジトリ内へ、Google DriveやGASの秘密情報を置かない
- 許可された端末だけがGASへアップロードできる
- 端末紛失時に管理者が端末を無効化できる
- フロントから任意のGoogle DriveフォルダIDを指定できない
- GAS側がBase・撮影日・伝票番号・撮影区分から保存先を決定する
- UploadIDによる二重登録防止を行う
- GPS、位置情報、フォークリフト導線取得はReturnSnapへ実装しない
- 全国展開前に、複数Base・複数端末での負荷試験とGAS割り当て確認を完了する

### 初期試運転の合格基準

- 員数用10台、リフトマン用4台でホーム画面から起動できる
- iPhoneの最新OSで、CountとLiftが別アイコン・別入口として動作する
- 1伝票30枚をオフラインで撮影し、アプリ再起動後も復元できる
- 20枚のアップロード途中で通信を切断し、再接続後に重複なしで完了できる
- Driveの保存先、ファイル名、UploadLogが仕様どおり一致する
- 荷姿写真が全体1枚・細部2枚未満では保存できない
- 未送信データがある状態でアプリを更新してもデータが失われない
- 現場試運転で、利用者が重大な迷いなく操作できる
